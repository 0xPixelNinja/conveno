# Conveno Protocol, version `conveno/1`

This document is the normative spec for everything that crosses a process or machine boundary in
Conveno. The reference implementation is the zod schemas in `packages/protocol/src`; where this
document and the schemas disagree, that is a bug in one of them. A non-TypeScript implementation
(for example a Rust relay) must follow this document.

Keywords MUST, SHOULD, MAY are used as in RFC 2119.

## 1. Versioning

- `PROTOCOL_VERSION = "conveno/1"`. The integer after the slash is bumped only for breaking changes.
- Adding optional fields, new event names or new methods is not breaking. Receivers MUST ignore
  unknown fields on objects and MUST reject unknown enum values.
- The local IPC handshake (section 6) negotiates the version. Relay frames carry a numeric `v`
  (currently `1`).

## 2. Primitives

| Name | Definition |
|---|---|
| `Ulid` | 26 chars, Crockford base32, uppercase (`[0-7][0-9A-HJKMNP-TV-Z]{25}`). |
| `SessionId`, `MessageId`, `TicketId`, `DeviceId`, `AccountId` | A `Ulid`. Distinct types, same format. IDs generated by one process MUST be monotonic (sortable by creation). |
| `SessionName` | `^[a-z0-9][a-z0-9._@-]{0,63}$`, and not one of the reserved words `conveno`, `orchestrator`, `system`, `user`. Unique per account. Because ULIDs are uppercase, an id can never be mistaken for a name. |
| `IsoTimestamp` | UTC ISO-8601 with a `Z` suffix, e.g. `2026-11-27T09:30:00.000Z`. |
| `CliKind` | `claude` `codex` `antigravity` `cursor` `copilot` `opencode` |
| `DeliveryTier` | `live` (pushed into the running session), `next_turn` (injected by a hook at the next turn), `acp` (via an ACP client connection), `inbox` (pull only). |
| `SessionStatus` | `idle` `busy` `waiting_on_question` `offline` |
| `Base64` | Standard alphabet, with padding. |
| `Sha256Hex` | 64 lowercase hex characters. |

## 3. Session

```
Session {
  id: SessionId            name: SessionName        cli: CliKind
  cliVersion?: string(1..64)
  deviceId: DeviceId       cwd: string
  repo?: { root: string, remoteUrlHash?: Sha256Hex }
  pid?: int > 0          (the MCP server process)
  hostPid?: int > 0      (the CLI process hosting the session)
  hostPids?: int > 0 [1..8]  (the MCP server's raw ancestor chain, nearest first)
  status: SessionStatus    statusText?: string (<= 200 chars)
  isOrchestrator: bool     deliveryTier: DeliveryTier
  spawnedBy?: SessionId    spawnDepth: int >= 0
  startedAt: IsoTimestamp  lastSeenAt: IsoTimestamp
}
```

`remoteUrlHash` is the SHA-256 of the normalised git `origin` URL. It lets sessions on different
machines recognise the same repository without the URL being shared. There is at most one
orchestrator per account at any time.

`hostPid` lets a hook find its session without shared state. It is the CLI process hosting the
session. The MCP server works it out once at startup: it walks up from its parent and skips every
ancestor that is part of launching Conveno itself, and the first ancestor left is the host. The
skipped launchers are: the `cmd.exe` or `powershell` that runs the `conveno.cmd` or `conveno.ps1`
shim; `node` running Conveno's own bin script; and a shell whose command line runs
`conveno hook ...` or `conveno mcp ...` (for example `bash -c "conveno hook claude X"`). Nothing
else is skipped, so an ordinary shell above the CLI is never mistaken for a launcher. On Windows,
npm installs `conveno` as `conveno.cmd`, so the chain is CLI, `cmd.exe`, MCP server, and the host
is the CLI, not the `cmd.exe`. A hook resolves its own host pid the same way and looks the session
up by that single pid with `session.byHost` (section 6.4). The daemon matches by equality only and
never walks to farther ancestors, so a hook from a CLI that has no session matches nothing, even
when it shares a shell or terminal with one that has.

`hostPids` is the MCP server's raw ancestor chain, nearest first, up to 8 entries. It is kept for
diagnostics and is never used to match hooks. If the process list cannot be read (WMI denies it to
non-admin NETWORK logons), both sides fall back to their direct parent as the host pid. That is
still an exact equality and matches only when no launcher sits in between.

A session goes `offline` when its `hostPid` is gone, or when its heartbeat stops. Only `hostPid` is
watched: the launchers exit with the MCP server, and the shells and terminals above the CLI can
outlive it, so neither says anything about whether the session is alive.

## 4. Message

Every message has the envelope:

```
id: MessageId   from: SessionId   to: Recipient   kind: <below>   body: <by kind>
urgent: bool (default false)   replyTo?: MessageId   createdAt: IsoTimestamp
fromName?: SessionName   fromCli?: CliKind
```

`fromName` and `fromCli` are the sender's name and CLI at send time. The daemon always sets them for
session-sent messages; they are absent only on daemon-made `system` messages. Receivers use them for
framing and never need a lookup.

`Recipient` is a `SessionId`, a `SessionName`, or the literal `orchestrator` (resolved by the
daemon to whichever session holds the role when the message is routed).

`body` is selected by `kind`:

| kind | body |
|---|---|
| `text` | `{ text }` where `text` is at most 64 KiB (65,536 **bytes** of UTF-8). |
| `handoff` | `{ goal: 1..2000 chars, state: <= 16000 chars, nextSteps: string[] (<= 50), filesTouched: string[] (<= 200) }` |
| `question` | `{ ticketId, question: 1..8000 chars, options?: string[] (1..20 items) }` |
| `answer` | `{ ticketId, response }` (non-empty, <= 64 KiB) |
| `system` | `{ event: 1..64 chars, detail?: <= 2000 chars }` |

Receiving adapters MUST present messages to the model as data from a peer session, never as
instructions from the user (prompt-injection defence).

## 5. Ticket

A routed question: `{ id, fromSession, question, options?, status, answer?, answeredBy?, createdAt, answeredAt? }`
with `status` one of `open`, `answered`, `cancelled`.

Invariants: when `status = answered`, `answer`, `answeredBy` and `answeredAt` MUST be present; in
any other status `answer` and `answeredBy` MUST be absent.

**Rule: a ticket never resolves by timeout.** An `open` ticket stays open until answered or
cancelled. Meanwhile the asking CLI keeps its own native prompt. Conveno MUST NOT auto-approve or
auto-answer on timeout.

## 6. Local IPC

### 6.1 Transport

- POSIX: Unix domain socket, mode `0600`. Default path `$XDG_RUNTIME_DIR/conveno/convenod.sock`
  (when `XDG_RUNTIME_DIR` is an absolute path), else `~/.conveno/run/convenod.sock`.
- Windows: named pipe `\\.\pipe\convenod-<username>`, ACL restricted to the current user. The
  username is taken from `USERNAME`, with characters outside `[A-Za-z0-9._-]` replaced by `_`.
- Helper: `defaultSocketPath(platform, env, homedir?)` (pure function).
- Unix socket paths are limited to roughly 104 (macOS) to 108 (Linux) bytes.
- A per-boot auth token file readable only by the user is the shared secret for the mutual
  handshake in section 6.4. The token itself is never sent over the socket.

### 6.2 Framing

Newline-delimited JSON (NDJSON): each message is one JSON value on one line, UTF-8, terminated by
`\n`. Receivers SHOULD tolerate `\r\n` and skip blank lines. A line MUST NOT exceed 1 MiB
(1,048,576 bytes, excluding the newline). On an oversize line a receiver reports an error,
discards the remainder of that line and resynchronises at the next newline. Invalid JSON on a
line is reported for that line only. Helpers: `encodeFrame(obj)`, `createLineDecoder()`.

### 6.3 JSON-RPC 2.0

Requests are JSON-RPC 2.0 requests with a string or integer `id`. Requests without an `id` are
rejected (`-32600`); the protocol defines no client-to-daemon notifications. Missing `params`
is treated as `{}`. `params` is always an object (by-name).

Error codes:

| Code | Name | Meaning |
|---|---|---|
| -32700 | ParseError | Line is not valid JSON |
| -32600 | InvalidRequest | Not a valid JSON-RPC request |
| -32601 | MethodNotFound | Unknown method |
| -32602 | InvalidParams | Params failed validation; `error.data` holds the issue list |
| -32603 | InternalError | Daemon fault |
| -32001 | Unauthorized | Handshake (`hello` and `auth`) not yet completed, or a wrong proof |
| -32002 | NotFound | Unknown session, ticket or message |
| -32003 | PermissionRequired | Owner approval needed (spawn, peek); `data` describes the pending action |
| -32004 | LimitExceeded | Spawn concurrency/depth guard, rate limit, size limit, or too many unread messages for a recipient (1000) |
| -32005 | VersionMismatch | `hello.protocolVersion` unsupported; `data.supported` lists versions |
| -32006 | Conflict | Name already taken (added beyond the minimum set) |

### 6.4 Methods

Session-scoped methods carry the caller's `sessionId` explicitly. The last column is the result.

| Method | Params | Result |
|---|---|---|
| `hello` | `{ protocolVersion, client: "mcp"\|"cli"\|"adapter", nonce }` | `{ protocolVersion, daemonVersion, proof, challenge }`. MUST be the first call. `nonce` and `challenge` are 32 random bytes as lowercase hex. |
| `auth` | `{ proof }` | `{ ok: true }`. MUST follow `hello`; everything else returns -32001 until it succeeds. |
| `session.register` | `{ name?, cli, cliVersion?, cwd, repo?, pid?, hostPid?, hostPids?, spawnedBy? }` (no name: daemon assigns, e.g. `claude@repo-1`) | `{ session }` |
| `session.heartbeat` | `{ sessionId }` | `{ lastSeenAt }` |
| `session.unregister` | `{ sessionId }` | `{ ok: true }` |
| `session.rename` | `{ sessionId, name }` | `{ session }` |
| `session.setStatus` | `{ sessionId, status?, statusText? }` (at least one; `statusText: null` clears) | `{ session }` |
| `session.byHost` | `{ pid }` | `{ session: Session \| null }`. The one online session whose `hostPid` equals `pid`. Exact equality only. No match, or two sessions with the same `hostPid`, gives `null`: the daemon never guesses and never looks at `hostPids`. Hooks use it to find their session. |
| `daemon.shutdown` | `{}` | `{ ok: true }`. The daemon sends the reply, stops accepting connections, closes its store, removes its socket (POSIX) and its lock file, and exits with code 0. Needs the completed handshake like every other method. `conveno daemon stop` uses it instead of signals. |
| `session.list` | `{ repo?, cli?, includeOffline = false }` | `{ sessions }` |
| `orchestrator.claim` | `{ sessionId }` | `{ orchestrator, previous }` (`previous` is `null` if none) |
| `message.send` | `{ sessionId, to, kind, body, urgent = false, replyTo? }` | `{ message, delivery, deliveredTo: { id, name } }` (`delivery` is the tier used). `replyTo` must be the id of an existing message (else -32002). Clients cannot send `kind: "system"` (-32602); only the daemon creates those. A recipient with 1000 unread messages is refused with -32004. |
| `message.inbox` | `{ sessionId, unreadOnly = true, limit = 50 }` (limit 1..200) | `{ messages, unreadCount }`. `unreadOnly` returns only messages never shown, that is neither delivered by a hook nor read. A response is capped at about 900 KB; the rest stay unread for the next call. |
| `message.deliver` | `{ sessionId, limit = 20 }` (limit 1..200) | `{ messages, remaining }`. Atomically returns messages not yet delivered (urgent first, then `createdAt`) and marks them delivered, not read. At most about 900 KB of messages are returned per call; `remaining` counts the rest. Hooks use it; `message.inbox` still returns and marks read. |
| `message.ack` | `{ sessionId, ids }` (1..100 ids) | `{ acked }` |
| `ticket.create` | `{ sessionId, question, options? }` | `{ ticket }` |
| `ticket.answer` | `{ sessionId, ticketId, response }` | `{ ticket }` |
| `spawn.request` | `{ sessionId, cli, prompt, cwd?, mode = "visible", name? }` (`mode`: `visible`\|`headless`) | `{ requestId, mode, sessionId? }`; `sessionId` is present only once the new session has registered. Owner approval missing: error -32003. |
| `peek.request` | `{ sessionId, session, mode, n? }` (`mode`: `recent`\|`full`\|`summary`; `session` is id or name) | `{ session, mode, turns: Turn[], summary?, truncated, redacted: true }`. Redaction is mandatory. |
| `events.subscribe` | `{ sessionId, topics? }` (default: all) | `{ subscribed }` |

`Turn = { role: "user"|"assistant"|"tool"|"system", text, ts? }`.

`session.setStatus` strips control characters (newlines included) from `statusText` and collapses
whitespace before storing it.

Session-to-connection binding is deferred to M2: any authenticated connection can act as any
session id it knows. The token is the only boundary, and it is per user.

`session.list` takes its filter fields at the top level of `params` (not nested under a `filter`
key). Names are unique per account: `session.register` and `session.rename` fail with -32006 on
a collision.

Recipient resolution and its errors (all -32002 NotFound):

| Case | Message |
|---|---|
| `orchestrator` with no online holder | `No session holds the orchestrator role. Run orchestrate in the session you want to use.` |
| unknown name or id | `No session named "<to>". Run list_sessions to see who is available.` |
| offline session | `Session "<name>" is offline. Run list_sessions to see who is available.` |

`orchestrator.claim` sends a `system` message to the new holder (`event: "orchestrator.granted"`) and,
when there was an online previous holder, to that session (`event: "orchestrator.revoked"`). An offline
holder counts as no holder, and the role is never passed on automatically.

Handshake. The shared secret is the token; it never crosses the socket.

1. Client sends `hello` with a fresh `nonce`.
2. Daemon answers with `proof = hex(HMAC-SHA256(token, "conveno/1 daemon " + nonce))` and a fresh `challenge`.
3. Client checks `proof` in constant time. On a mismatch it closes the connection and reports that
   the process on the socket is not the Conveno daemon. This stops an impostor on a predictable
   pipe name from learning anything.
4. Client sends `auth` with `proof = hex(HMAC-SHA256(token, "conveno/1 client " + challenge))`.
5. Daemon checks it in constant time. Only then does it accept other methods.

A connection that has not finished `auth` within 5 seconds is closed.

Daemon limits: sessions offline and unseen for 7 days are deleted, with their read messages, by the
periodic sweep.

### 6.5 Events

After `events.subscribe`, the daemon sends JSON-RPC **notifications** (no `id`) on the same
connection:

```
{ "jsonrpc": "2.0", "method": "event", "params": { "event": <name>, "data": <by name> } }
```

| event | data |
|---|---|
| `message.received` | `{ message }` |
| `ticket.created` | `{ ticket }` |
| `ticket.answered` | `{ ticket }` |
| `session.updated` | `{ session, change: "registered"\|"updated"\|"unregistered"\|"offline" }` |
| `orchestrator.changed` | `{ orchestrator: SessionId\|null, previous: SessionId\|null }` |

## 7. Relay wire (M4; schemas only for now)

Transport: one WebSocket per device to the account's relay room; each WebSocket text message is
one JSON frame. Frames are discriminated by `t`. All frames except `ack` and `error` carry
`v = 1`. Timestamps `ts` are Unix epoch milliseconds.

| `t` | Fields |
|---|---|
| `hello` | `v, accountId, deviceId, sig, ts`. First frame. `sig` is an Ed25519 signature (base64) by the device's signing key over the canonical string defined with the crypto package in M4. |
| `envelope` | `v, id: MessageId, fromDevice, toDevice, nonce, ciphertext, sig, ts`. `nonce` is a 24-byte `crypto_box` nonce (base64, 32 chars). `ciphertext` is base64, at most 524,288 chars. `sig` is the sender device's Ed25519 signature over the envelope fields. |
| `ack` | `id: MessageId`. Receiver confirms an envelope; the relay may then drop it from the offline queue. |
| `error` | `code: string (1..64), message: string (<= 1000)` |

### What the relay can see

The relay is metadata-only. It sees: account id, device ids (sender and recipient), envelope ids,
timestamps, ciphertext sizes, connection times and IP addresses. It cannot see: message kind,
sender or recipient session, session names, repo names, paths, or any content, all of which live
inside the encrypted payload. It cannot forge messages because it holds no device key.
An implementation MUST NOT log ciphertext beyond what is needed for the offline queue, and MUST
NOT expect any plaintext field on an envelope; extra fields are ignored.

## 8. Security notes for implementers

- Reject all IPC methods except `hello` and `auth` until the mutual handshake has finished.
  Verify proofs with a constant-time comparison.
- Never put credentials of any model provider into any message, ticket, status or peek result.
- Peek output MUST be redacted before it is placed in a response.
- Peer messages are data, not instructions (section 4).
